# Avantime Connect — Windows, регистрация и VPN

Основа: `79ae8b9cba61515fd116c15f77198ae6bd77a7be`. Требования: Windows 11 x64,
.NET SDK 8, установленный официальный WireGuard (`Program Files\WireGuard\wg.exe`).
Регистрация выполняется без повышения прав. Кнопки подключения, отключения и проверки
VPN запускают отдельный короткоживущий процесс через UAC. На этом этапе поддержано
повышение **той же учётной записи Windows**; ввод другого администратора отклоняется.
Профиль DPAPI CurrentUser остаётся у пользователя, выполнившего регистрацию.

## Сборка и проверка

Из корня checkout, PowerShell:

```powershell
dotnet build .\windows-client\AvantimeConnect.sln -c Release
if ($LASTEXITCODE -ne 0) { throw "Сборка не завершена" }
dotnet run --project .\windows-client\tests\AvantimeConnect.Checks -c Release --no-build
if ($LASTEXITCODE -ne 0) { throw "Проверки не пройдены" }
dotnet run --project .\windows-client\src\AvantimeConnect.App -c Release --no-build
```

Проверки не обращаются к настоящему API, не создают VPN peers и не меняют туннели.
На Windows проверяют также DPAPI round-trip и повреждённый файл; при установленном
WireGuard создают временную пару ключей в памяти без вывода значений.

## Первый запуск

Окно просит адрес API, имя устройства и **токен приглашения**. Администраторский
ключ не используется. Приглашение получают через административный интерфейс
для отдельного тестового пользователя. Само нажатие «Зарегистрировать компьютер»
обращается к настоящему API и может создать VPN peer — это не локальная проверка.

Адрес — HTTPS origin без пути, например адрес, подтверждённый администратором.
Не отключать проверку сертификата. HTTP разрешён только с буквальным `127.0.0.1`
или `[::1]`, для заранее настроенного SSH-туннеля на том же Windows-компьютере.
Работающий туннель на Mac не делает этот адрес доступным на Windows.
Публичный домен не считается настроенным только потому, что он существует в DNS.
Автоматические HTTP redirects отключены, приглашение на другой адрес не пересылается.

Клиент вызывает `wg.exe genkey/pubkey`, сохраняет identity **до POST /api/enroll/**.
Только public_key, token, device_name уходят на сервер. Приватный ключ, приглашение
и полученный профиль сохраняются вместе с DPAPI CurrentUser в:

`%LOCALAPPDATA%\AvantimeConnect\enrollment.dpapi`

Один файл блокировки защищает запись даже между Windows-сеансами. Запись атомарная:
сначала зашифрованный временный файл, flush, затем замена. Значения секретов и сырые
ошибки сервера не выводятся в интерфейс/журнал. Это не защита от программ, работающих
под тем же пользователем Windows или администратором компьютера.

После ошибки/таймаута и перезапуска восстанавливаются тот же ключ, приглашение,
адрес и имя устройства. Автоматической смены ключей нет. При сохранённом профиле
клиент не повторяет регистрацию, но и **не утверждает**, что устройство сейчас
активно на сервере. Локальный профиль не является проверкой текущего отзыва.

Не удалять enrollment.dpapi, чтобы «исправить» неопределённый исход. Сервер уже мог
создать peer. Замену identity/переезд/отзыв должен согласовать администратор; интерфейс
удаления/нового устройства в этот этап не входит.

## Подключение VPN

Обновление клиента не меняет сохранённую регистрацию. После запуска отображаются
прежний VPN IP и кнопки «Подключить VPN», «Отключить VPN», «Проверить VPN».
Повторно вводить приглашение не нужно. Проверка API/SSH нужна для регистрации;
WireGuard соединяется с endpoint из сохранённого профиля отдельно, по UDP.

Поддерживаемая политика этого пилота: адрес устройства 10.30.0.2–10.30.0.239,
ровно маршрут 10.40.0.0/24, PersistentKeepalive 25. Серверный адрес .1 и диапазон
.240–.255 не допускаются. Другие маршруты, включая две половины default route,
отклоняются. DNS, default gateway, сеть управления 10.20.0.0/24 не настраиваются.
Клиент не отключает чужие VPN; подключение блокируется при другой активной службе
WireGuard. Перед пилотным подключением оператор должен убедиться, что его текущий
сеанс управления не зависит от маршрута 10.40.0.0/24.

Имя туннеля `avt-<24 hex>` стабильно выводится из SHA-256 открытого ключа устройства.
Проверяются соответствие private/public key, владелец и ACL каталога/файла,
отсутствие reparse points, сохранённое содержимое и точная команда службы.
Существующие несовпадающие конфигурации/службы не заменяются. Конфигурация не содержит
скриптов, DNS, приглашения или администраторского API-ключа.

Служба — штатная `WireGuardTunnel$<имя>`, созданная установленным WireGuard.
Её `.conf.dpapi` хранится в `%ProgramFiles%\AvantimeConnect.Tunnels\`.
Для совместимости с LocalSystem используется native DPAPI Machine scope с именем
туннеля в description и без entropy. **Machine DPAPI сам по себе доступен всем
пользователям машины**: каталог и файлы имеют ACL только Administrators и SYSTEM.
Исходная регистрация по-прежнему защищена отдельно через DPAPI CurrentUser.
Открытая конфигурация существует только в памяти, не записывается в `.conf`/temp,
не передаётся в аргументах, не выводится в лог. Администратор машины может получить
доступ к обоим видам данных; защита не обещает противодействия локальному администратору.

После установки служба переводится на ручной запуск. Если установка частично
завершилась с ошибкой, helper также пытается установить ручной запуск, проверив
принадлежность службы. При аварийном завершении Windows/процесса в этот короткий
промежуток остаётся штатный automatic start WireGuard: оператор должен проверить
состояние, а затем выполнить подключение/отключение для завершения настройки.
Закрытие окна не отключает VPN. Отключение останавливает только свою службу,
сохраняет конфигурацию и не отзывает peer на сервере.

«Служба работает» не означает установленное VPN-соединение. Проверяются runtime
public key, единственный ожидаемый peer, его маршруты и latest-handshake.
Успех показывается только для handshake не старше 180 секунд, без будущих дат.
Подключение ждёт до 35 секунд свежего handshake; при его отсутствии служба остаётся
запущенной и интерфейс явно сообщает, что соединение не подтверждено. Проверка
показывает время снимка состояния; это не непрерывный мониторинг и не проверка RDP
или текущего отзыва через API. Можно проверить повторно или отключить VPN.

Ручная проверка на DEV-ADMIN: подтвердить восстановление прежнего профиля и IP;
подключить VPN через UAC; получить свежий handshake; отключить и проверить остановку;
повторно подключить без новой регистрации. Для пересылки результата достаточно
строки состояния. Не публиковать `showconf`, `wg ... dump`, приватные ключи или файлы профиля.

Основания реализации: [WireGuard Enterprise Usage](https://github.com/WireGuard/wireguard-windows/blob/master/docs/enterprise.md),
[формат DPAPI WireGuard](https://github.com/WireGuard/wireguard-windows/blob/master/conf/dpapi/dpapi_windows.go),
[Microsoft CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

## Границы этапа

Реализовано: WPF-окно, генерация ключей, защищённое сохранение и восстановление,
регистрация, проверка и сохранение профиля, управление собственным туннелем с UAC,
проверка runtime identity/handshake, понятные состояния ошибок.

Пока **не реализованы** подключение DEV по RDP, RemoteApp, автообновление,
установщик, смена identity и elevation под другой учётной записью.
Серверный контракт пока возвращает один rdp_host; DEV/PROD нельзя достоверно
вывести из него. Приватный ключ не экспортируется в обычный `.conf`.

## Проверки разработки

Логика Core и консольные проверки компилируются Roslyn из .NET SDK 8.0.425.
Linux-прогон не заменяет Windows: DPAPI и реальный wg.exe там пропускаются.
GitHub Actions Windows client собирает настоящую WPF solution и запускает проверки
DPAPI на Windows. Запуск окна и реальную регистрацию проверяет оператор отдельно.

Дополнительный CI smoke-test устанавливает официальный подписанный WireGuard 1.1.1
на одноразовом GitHub-hosted Windows runner. Он создаёт отдельную случайную identity,
использует UDP endpoint только 127.0.0.1:9, проверяет чтение encrypted config службой
LocalSystem, runtime key/route, отсутствие ложного handshake, manual start,
остановку и повторный запуск. Затем удаляет только свою тестовую службу/конфигурацию.
Режим `--tunnel-smoke` запрещён вне GitHub-hosted runner. Обычный запуск Checks
никогда не создаёт туннели. UAC и связь с настоящим VPN-сервером проверяет оператор.

## Открыть PROD

После восстановления зарегистрированного профиля форма регистрации скрывается,
чтобы кнопки VPN и рабочего стола были видны сразу. Кнопка «Открыть PROD» доступна
только для профиля desktop с rdp_host=10.40.0.20 (адрес подтверждён оператором).
Перед запуском выполняется новая проверка собственной службы/handshake через UAC,
затем TCP-проверка 10.40.0.20:3389 с привязкой к сохранённому VPN IP (таймаут 8 с).
При ошибке mstsc не запускается. Пароли в приложении не вводятся и не сохраняются:
стандартный mstsc.exe запускается из системного каталога с единственным аргументом
/v:10.40.0.20. Учётные данные и проверку сертификата обрабатывает Windows.
Это проверка доступности перед запуском, не сетевой kill switch: последующее изменение
маршрутов может повлиять на RDP. Отключение VPN не завершает mstsc принудительно.

DEV подтверждён как 10.20.0.20, но не включён в текущий VPN-профиль. Кнопка DEV
до отдельной настройки/проверки доступа не добавляется. Реальная проверка оператора:
после обновления открыть прежний профиль, подключить VPN, нажать «Открыть PROD»,
войти в Windows. При остановленном VPN запуск из кнопки должен блокироваться.
