# Avantime Connect — Windows, регистрация и VPN

Основа: `79ae8b9cba61515fd116c15f77198ae6bd77a7be`. Требования для разработки: Windows 10/11 x64,
.NET SDK 8, установленный официальный WireGuard (`Program Files\WireGuard\wg.exe`).
Регистрация и управление VPN выполняются обычным пользователем. Setup один раз
устанавливает LocalSystem-службу AvantimeConnectBroker с правами администратора.
Профиль DPAPI CurrentUser остаётся у пользователя, выполнившего регистрацию.

## Сборка и проверка

Из корня checkout, PowerShell:

```powershell
dotnet build .\windows-client\AvantimeConnect.sln -c Release
if ($LASTEXITCODE -ne 0) { throw "Сборка не завершена" }
dotnet run --project .\windows-client\tests\AvantimeConnect.Checks -c Release --no-build
if ($LASTEXITCODE -ne 0) { throw "Проверки не пройдены" }
dotnet run --project .\windows-client\src\AvantimeConnect.App -c Release --no-build
```

Проверки не обращаются к настоящему API, не создают VPN peers и не меняют туннели.
На Windows проверяют также DPAPI round-trip и повреждённый файл; при установленном
WireGuard создают временную пару ключей в памяти без вывода значений.

## Первый запуск

Окно просит адрес API, имя устройства и **токен приглашения**. Администраторский
ключ не используется. Приглашение получают через административный интерфейс
для отдельного тестового пользователя. Само нажатие «Зарегистрировать компьютер»
обращается к настоящему API и может создать VPN peer — это не локальная проверка.

Адрес — HTTPS origin без пути, например адрес, подтверждённый администратором.
Не отключать проверку сертификата. HTTP разрешён только с буквальным `127.0.0.1`
или `[::1]`, для заранее настроенного SSH-туннеля на том же Windows-компьютере.
Работающий туннель на Mac не делает этот адрес доступным на Windows.
Публичный домен не считается настроенным только потому, что он существует в DNS.
Автоматические HTTP redirects отключены, приглашение на другой адрес не пересылается.

Клиент вызывает `wg.exe genkey/pubkey`, сохраняет identity **до POST /api/enroll/**.
Только public_key, token, device_name уходят на сервер. Приватный ключ, приглашение
и полученный профиль сохраняются вместе с DPAPI CurrentUser в:

`%LOCALAPPDATA%\AvantimeConnect\enrollment.dpapi`

Один файл блокировки защищает запись даже между Windows-сеансами. Запись атомарная:
сначала зашифрованный временный файл, flush, затем замена. Значения секретов и сырые
ошибки сервера не выводятся в интерфейс/журнал. Это не защита от программ, работающих
под тем же пользователем Windows или администратором компьютера.

После ошибки/таймаута и перезапуска восстанавливаются тот же ключ, приглашение,
адрес и имя устройства. Автоматической смены ключей нет. При сохранённом профиле
клиент не повторяет регистрацию, но и **не утверждает**, что устройство сейчас
активно на сервере. Локальный профиль не является проверкой текущего отзыва.

Не удалять enrollment.dpapi, чтобы «исправить» неопределённый исход. Сервер уже мог
создать peer. Замену identity/переезд/отзыв должен согласовать администратор; интерфейс
удаления/нового устройства в этот этап не входит.

## Подключение VPN

Обновление клиента не меняет сохранённую регистрацию. После запуска отображаются
прежний VPN IP и кнопки «Подключить VPN», «Отключить VPN», «Проверить VPN».
Повторно вводить приглашение не нужно. Проверка API/SSH нужна для регистрации;
WireGuard соединяется с endpoint из сохранённого профиля отдельно, по UDP.

Поддерживаемая политика этого пилота: адрес устройства 10.30.0.2–10.30.0.239,
маршруты PROD 10.40.0.0/24, DEV 10.20.0.20/32 или оба по назначению,
PersistentKeepalive 25. Серверный адрес .1 и диапазон
.240–.255 не допускаются. Другие маршруты, включая две половины default route,
отклоняются. DNS, default gateway, сеть управления 10.20.0.0/24 не настраиваются.
Клиент не отключает чужие VPN; подключение блокируется при другой активной службе
WireGuard. Перед пилотным подключением оператор должен убедиться, что его текущий
сеанс управления не зависит от маршрута 10.40.0.0/24.

Имя туннеля `avt-<24 hex>` стабильно выводится из SHA-256 открытого ключа устройства.
Проверяются соответствие private/public key, владелец и ACL каталога/файла,
отсутствие reparse points, сохранённое содержимое и точная команда службы.
При обновлении разрешены только изменения между указанными наборами маршрутов
в собственном остановленном туннеле. Ключи, адрес, endpoint и peer должны совпадать;
чужие конфигурации/службы не заменяются. Конфигурация не содержит
скриптов, DNS, приглашения или администраторского API-ключа.

Служба — штатная `WireGuardTunnel$<имя>`, созданная установленным WireGuard.
Её `.conf.dpapi` хранится в `%ProgramFiles%\AvantimeConnect.Tunnels\`.
Для совместимости с LocalSystem используется native DPAPI Machine scope с именем
туннеля в description и без entropy. **Machine DPAPI сам по себе доступен всем
пользователям машины**: каталог и файлы имеют ACL только Administrators и SYSTEM.
Исходная регистрация по-прежнему защищена отдельно через DPAPI CurrentUser.
Открытая конфигурация существует только в памяти, не записывается в `.conf`/temp,
не передаётся в аргументах, не выводится в лог. Администратор машины может получить
доступ к обоим видам данных; защита не обещает противодействия локальному администратору.

После установки служба переводится на ручной запуск. Если установка частично
завершилась с ошибкой, контроллер также пытается установить ручной запуск, проверив
принадлежность службы. При аварийном завершении Windows/процесса в этот короткий
промежуток остаётся штатный automatic start WireGuard: оператор должен проверить
состояние, а затем выполнить подключение/отключение для завершения настройки.
Закрытие окна не отключает VPN. Отключение останавливает только свою службу,
сохраняет конфигурацию и не отзывает peer на сервере.

«Служба работает» не означает установленное VPN-соединение. Проверяются runtime
public key, единственный ожидаемый peer, его маршруты и latest-handshake.
Успех показывается только для handshake не старше 180 секунд, без будущих дат.
Подключение ждёт до 35 секунд свежего handshake; при его отсутствии служба остаётся
запущенной и интерфейс явно сообщает, что соединение не подтверждено. Проверка
показывает время снимка состояния; это не непрерывный мониторинг и не проверка RDP
или текущего отзыва через API. Можно проверить повторно или отключить VPN.

Ручная проверка на DEV-ADMIN: подтвердить восстановление прежнего профиля и IP;
подключить VPN через службу; получить свежий handshake; отключить и проверить остановку;
повторно подключить без новой регистрации. Для пересылки результата достаточно
строки состояния. Не публиковать `showconf`, `wg ... dump`, приватные ключи или файлы профиля.

Основания реализации: [WireGuard Enterprise Usage](https://github.com/WireGuard/wireguard-windows/blob/master/docs/enterprise.md),
[формат DPAPI WireGuard](https://github.com/WireGuard/wireguard-windows/blob/master/conf/dpapi/dpapi_windows.go),
[Microsoft CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata).

## Границы этапа

Реализовано: WPF-окно, генерация ключей, защищённое сохранение и восстановление,
регистрация, проверка и сохранение профиля, управление собственным туннелем через службу,
проверка runtime identity/handshake, понятные состояния ошибок.

Реализованы отдельные назначения DEV/PROD и обновление доступа без смены identity.
Пока **не реализованы** автоматическая выдача файлов RemoteApp, автообновление и перенос identity между учётными
записями Windows. Приватный ключ не экспортируется в обычный `.conf`.

## Проверки разработки

Логика Core и консольные проверки компилируются Roslyn из .NET SDK 8.0.425.
Linux-прогон не заменяет Windows: DPAPI и реальный wg.exe там пропускаются.
GitHub Actions Windows client собирает настоящую WPF solution и запускает проверки
DPAPI на Windows. Запуск окна и реальную регистрацию проверяет оператор отдельно.

Дополнительный CI smoke-test устанавливает официальный подписанный WireGuard 1.1.1
на одноразовом GitHub-hosted Windows runner. Он создаёт отдельную случайную identity,
использует UDP endpoint только 127.0.0.1:9, проверяет чтение encrypted config службой
LocalSystem, runtime key/route, отсутствие ложного handshake, manual start,
остановку и повторный запуск. Затем удаляет только свою тестовую службу/конфигурацию.
Режим `--tunnel-smoke` запрещён вне GitHub-hosted runner. Обычный запуск Checks
никогда не создаёт туннели. GUI и связь с настоящим VPN-сервером проверяет оператор.

## Открыть DEV / PROD

После регистрации доступны только кнопки назначенных окружений для профиля desktop:
DEV — 10.20.0.20:3389, PROD — 10.40.0.20:3389. Legacy-профиль без environments
считается PROD-only. Сервер независимо ограничивает трафик управляемых VPN-устройств.
Перед запуском проверяются собственная служба/handshake и TCP-доступ к выбранному
серверу с привязкой к сохранённому VPN IP (таймаут 8 секунд). Затем запускается
системный mstsc.exe с фиксированным /v:адрес. Пароли обрабатывает Windows.
Это проверка доступности перед запуском, не сетевой kill switch: последующее изменение
маршрутов может повлиять на RDP. Отключение VPN не завершает mstsc принудительно.

Для существующего устройства: администратор применяет назначение в админке;
пользователь отключает VPN, нажимает «Обновить доступ», подключает VPN снова.
Обновление сохраняет ключи/IP, проверяет монотонную ревизию и точное соответствие
маршрутов окружениям. Ошибка HTTP или проверки сохраняет прежний локальный профиль.
Новые приглашения не нужны. Порядок включения серверных ограничений:
[deploy/wireguard/ACCESS.md](../deploy/wireguard/ACCESS.md).

## Установщик 0.4.2 (пилот)

GitHub Actions выдаёт ZIP-артефакт `AvantimeConnect-Setup-0.4.2-x64`: внутри Setup.exe
и SHA256SUMS.txt. Это тестовая сборка без подписи издателя Avantime. Для массового
распространения требуется code-signing; предупреждения Windows не отключаются.

Setup устанавливает self-contained клиент в Program Files и создаёт общие ярлыки.
Git, SDK и отдельный .NET на клиентском компьютере не нужны. При отсутствии WireGuard
Setup скачивает официальный MSI 1.1.1 по HTTPS, сверяет SHA-256, зафиксированный при
сборке после проверки Authenticode/издателя, и запускает его без GUI и автозапуска
менеджера. Сам MSI не включается в дистрибутив Avantime. Установленный WireGuard
не обновляется и не заменяется. Неполная существующая установка требует ремонта.
Первичная установка требует Интернета. Setup спрашивает права администратора;
регистрация и подключение автоматически во время установки не выполняются.

После Setup приложение открывают обычным ярлыком под своим Windows-пользователем.
Это сохраняет правильного владельца DPAPI. API по умолчанию https://connect.avantime.lv;
имя машины подставляется автоматически, приглашение вводится пользователем.
Импорт существующего профиля не нужен: используется тот же LocalAppData-файл.
Обычному пользователю повышение прав для VPN не требуется. Установку/обновление
может подтвердить другой администратор; это не меняет владельца профиля.

Перед обновлением нужно закрыть клиент. Удаление блокируется при активных службах
WireGuardTunnel$avt-*; чужие туннели не останавливаются. Профили пользователей,
защищённые конфигурации и установленный WireGuard сохраняются даже при удалении.
Удаление не является отзывом устройства на сервере. Принудительного reboot нет;
если MSI требует reboot, Setup предлагает перезапуск.

CI на отдельном чистом Windows runner проверяет первую установку с загрузкой
WireGuard, self-contained apphost, ярлык, повторную установку и удаление, сохранность
контрольного файла профиля. Дополнительно два настоящих standard-user аккаунта проверяют IPC, CurrentUser DPAPI,
запуск тестового туннеля (только loopback), запрет чужого управления и сохранение профиля
при обновлении службы. Никакие production-ключи/приглашения не используются. GUI и реальный профиль проверяются
оператором на пилотном компьютере. Windows 10/11 x64; ARM64 не поддерживается.

Сборка вручную на Windows с .NET SDK 8 и Inno Setup 6:
`powershell -File windows-client/installer/Build-Installer.ps1`
Результат в artifacts/windows-installer (не коммитится). Одноразовый stage удаляется.

## Граница привилегий службы 0.3.1

IPC: локальный named pipe, PIPE_REJECT_REMOTE_CLIENTS, запрет Network SID,
ACL без CreateNewInstance для пользователей, FirstPipeInstance и один постоянный
server handle. Клиент сверяет PID сервера pipe с PID службы из SCM.
Запрос строго 30 байт: версия, одна из трёх команд, имя avt-<24 hex>. Ни путей,
ни ключей, ни команд shell в протоколе нет. Чтение ограничено 5 секундами.
Служба impersonates фактического caller, получает его LocalAppData через token,
читает и расшифровывает ограниченный 64 KiB CurrentUser DPAPI профиль под этим token.
Контроллер работает после возврата к SYSTEM. Производный ключ и имя проверяются;
служба принимает только текущий endpoint 65.21.22.189:51820 (и 127.0.0.1:9 для smoke).
Разрешены только фиксированные наборы маршрутов DEV/PROD, адреса .2–.239, без DNS/hooks.
SID-владелец закрепляется в защищённом .owner-файле. Чужой SID отклоняется даже
при наличии копии ключей. Старый helper --tunnel-helper отключён.

Служба не делает автоматический VPN connect при загрузке; WireGuard-туннель остаётся
manual-start. Остановка/обновление broker не отключает VPN. Удаление broker
разрешено только после остановки всех avt-туннелей. При повреждённой регистрации
или отсутствующей службе клиент предлагает ремонт, а не повторную регистрацию.
Профиль, созданный под администратором, не переносится другому Windows-пользователю:
нужна отдельная согласованная миграция, которую этот Setup не выполняет.

### Исправление установки 0.3.1

Подготовка, установка и удаление службы запускают встроенный PowerShell-скрипт
с `-ExecutionPolicy RemoteSigned` только для дочернего процесса. Политики
компьютера и пользователя не изменяются; групповые политики сохраняют приоритет.
CI проверяет первую установку, повторную установку и удаление при унаследованном
`Restricted`. Это воспроизводит сбой 0.3.0 на JELENA-PC2. При корпоративном
запрете скриптов требуется согласование с администратором, автоматического обхода нет.

В версии 0.4.1 выровнены размеры кнопок VPN и рабочих столов. DEV и PROD
расположены рядом; обновление доступа вынесено в отдельную строку с пояснением.


## 0.4.2: split DNS и проверка RemoteApp

Причина ошибки RemoteApp: рабочий VPN-маршрут не назначал системному DNS-клиенту
резолвер AD. Broker теперь применяет NRPT для `ad.avantime.lv` и `.ad.avantime.lv`
на `10.40.0.10` после подтверждения handshake. DNS остальных доменов не меняется.
Для старого DEV-only профиля защищённый туннель автоматически получает дополнительный
`10.40.0.10/32`; identity и пользовательский DPAPI-профиль сохраняются. PROD уже
содержит этот адрес в `10.40.0.0/24`. Default route не добавляется.

Правила помечены точными DisplayName/Comment, namespace и resolver. Эквивалентное
ручное правило сохраняется и используется; конфликтующее правило вызывает ошибку
DNS без перезаписи. Отключение VPN удаляет только собственные правила. При отсутствии
handshake и после внешней остановки туннеля служба сверяет состояние каждые 30 секунд.
Закрытие окна сохраняет VPN. При перезапуске broker состояние сверяется заново.
Удаление клиента выполняет очистку собственных правил. Ручное правило остаётся и
после отключения/удаления: оно принадлежит администратору, приложение его не присваивает.

Кнопка «Открыть RemoteApp…» принимает опубликованный прямой PROD `.rdp` для
`WIN-APP-PROD.AD.AVANTIME.LV:3389`: проверяет VPN, разрешение имени системным DNS,
затем TCP через адрес VPN. Содержимое файла и подпись не переписываются, проверки
подлинности не отключаются. Шлюзы, балансировщик, другие серверы/порты не поддержаны
этой проверкой. Двойной щелчок внешнего `.rdp` пользуется системным split DNS,
но не запускает предварительную проверку приложения.

Обновление: закрыть окно приложения, установить Setup 0.4.2 поверх существующей
версии с подтверждением администратора. Повторная регистрация не требуется.
Обычный пользователь отключает и снова подключает VPN. Для DEV-only сначала
обновить Windows-клиенты, затем helper/ACL VPN-сервера и backend согласно
`deploy/wireguard/ACCESS.md`. Не запускать старый install-server поверх нестандартного
наборa authorized_keys без проверки; DNS-исправление не требует замены SSH-ключей.

Реальные проверки пилота: на LIGET после подключения выполнить
`[System.Net.Dns]::GetHostAddresses("WIN-APP-PROD.AD.AVANTIME.LV")` без явного DNS,
проверить порт 3389, запустить опубликованное RemoteApp обычным пользователем,
проверить внешние сайты до/после отключения VPN. Эти проверки требуют рабочей сети
и учётных данных; успешные CI-проверки не заменяют их.

Выбор разрядности обозначает сохранённый файл; разрядность программы на сервере
по самому RDP достоверно определить нельзя. Тип профиля remoteapp32/remoteapp64
ограничивает видимый выбор, desktop допускает оба. Файл хранится в CurrentUser
DPAPI и заново проверяется перед запуском. «Выбрать файл…» заменяет выбранный слот.
Обновление сохраняет профиль регистрации и оба слота.

Админка показывает устройства, VPN-IP и состояние рядом с точным логином,
включая отозванные устройства. Изменения backend не требуются.
Статическая админка на /var/www/avantime-connect требует отдельного развёртывания
новой сборки frontend; Windows Setup её не обновляет.

macOS: минимальная целевая система Ventura 13.7.8, Intel и Apple Silicon.
Это требование следующего клиента, не готовая macOS-сборка.
Реальные испытания DNS/RemoteApp/RDP на LIGET и JELENA остаются отдельным
приёмочным этапом; CI проверяет изолированные Windows-сценарии.
