# VM 101: контролируемая интеграционная проверка Фаз 1–2

Статус: **не выполнена**. Этот документ и инструмент готовят реальный прогон;
локальные регрессии используют имитацию SSH/WireGuard и не закрывают гейт.
База рабочего backend/helper: `18b477c99b23a7615f182a100ccf1b34cdba8f54`.
Новый инструмент не меняет app/, helper, их протокол или Docker-образ API.

## Версии, доступ и границы

Оператор до запуска фиксирует полный SHA выбранного checkout (`git rev-parse HEAD`)
и проверяет фактически установленное и запущенное:

- SHA-256 `/usr/local/sbin/avantime-wg-helper` совпадает с
  `deploy/wireguard/helper.py` этого checkout. Путь журнала установщика:
  `/var/lib/avantime-wg-state/managed.json`. Файла VERSION нет.
- Backend запускается из этого же checkout. `manifest.json` инструмента содержит
  SHA-256 загруженных исходников app/, инструмента и исходника helper. Checkout
  во время запуска не менять; сверить manifest с выбранной ревизией. Один лишь
  SHA текущей ветки не доказывает версию другого уже запущенного backend.
- Контракт: add возвращает `created`, remove — `absence_confirmed`. При несовпадении
  установленного кода остановиться; согласованное обновление — отдельная операция.
- Изменения peers — только через штатный SSH transport и ограниченный helper,
  forced command/sudo, strict host-key. Никаких root-shell мутаций, изменений
  маршрутов/NAT/firewall/DNS, перезапусков WireGuard или боевых учёток.
- Независимые снимки runtime/config/managed.json и хеш установленного файла снимает
  оператор с отдельно разрешённым доступом только для чтения. Helper status этих
  файлов целиком не отдаёт. Секреты, приватные ключи, приглашения и Bearer — не в отчёт.
- Изменения managed.json/wg0.conf/runtime вне helper/flock во время прогона запрещены.
  Обычные работающие VPN-сессии не останавливаются. При изменении боевых peers —
  остановить тестовые мутации, сохранить доказательства и согласовать точечное
  восстановление; не восстанавливать общий конфиг и не делать массовый restart.

## Адреса и атомарный production-резерв

Нужны минимум три разных IP/новых ключа/приглашения; для отдельного J — четвёртый.
Адреса внутри 10.30.0.0/24, кроме network/broadcast, helper RESERVED и адресов
интерфейсов; свободны в production devices, managed.json, runtime и конфиге.
Проверяется также попадание в существующие сети AllowedIPs, а не только равенство /32.

Перед тестовыми enroll оператор подтверждает наличие уникального индекса vpn_ip
в production devices и что все production-выделители используют эту коллекцию.
Для каждого IP — **insert_one**, без upsert и без изменения существующего документа:

```json
{"vpn_ip": "<TEST_IP>", "kind": "reserved", "public_key": "reserved:<TEST_IP>"}
```

`DuplicateKeyError` — стоп и разбор. Неопределённый результат записи тоже требует
проверки, а не предположения об успехе. Если вставка выиграла гонку с production
регистрацией, вставка клиентского устройства получит конфликт до helper.add и
повторит IPAM. Резерв не координирует независимые БД и прямые вызовы helper.
После успешной вставки повторить проверку config/runtime/managed; при конфликте
не выполнять тест и не удалять чужие данные. Маркер остаётся после прогона.

В тестовую БД маркер не добавлять: он заблокирует единственный адрес /32.
Не добавлять тест-IP в RESERVED helper. Инструмент ниже **не создаёт production
резерв и не проверяет его существование**: это обязательное предусловие оператора.

| Комплект | Сценарии | Конечное состояние |
|---|---|---|
| 1 | A → B → C → I → F → G → H1 → H2 | revoked, peer отсутствует |
| 2 | D: отмена pending до add | revoked, peer отсутствует |
| 3 | E: потеря ответа после настоящего add | revoked, peer отсутствует |
| 4, если используется | J: отзыв при задержанном успешном add-ответе | revoked, peer отсутствует |

Для каждого комплекта — отдельная тестовая БД и конфигурация с его /32. В каждой
операции owner создаёт API; зафиксировать enrollment.owner / device._id / wg_owner
и сравнить с журналом helper. Не назначать owner или state вручную в MongoDB.

## Изолированный backend с управляемым сбоем

Инструмент: `admin-backend/integration/fault_backend.py`. Он запускается отдельно,
не подключается из app.main, не входит в обычный Dockerfile, не добавляет HTTP
маршрутов управления сбоем. Один процесс, без reload, только 127.0.0.1:18000.
Не подставлять его в production сервис. Обычный app/ и helper остаются неизменны.

Использовать отдельный экземпляр MongoDB и учётные данные только для тестовой БД.
Имя обязано соответствовать `avantime_connect_vm101_test_<run>` (суффикс: 1–30
строчных латинских букв, цифр или `_`). Проверка имени сама по себе не доказывает
изоляцию сервера и его прав: её подтверждает оператор.

Создать файл настроек **вне checkout**, с правами 0600. Пример структуры; все
значения в угловых скобках заменить проверенными, секреты вводить приватно:

```dotenv
mongo_uri=<URI отдельной тестовой MongoDB>
db_name=avantime_connect_vm101_test_d
vpn_client_pool=<TEST_IP2>/32
wg_mode=ssh
admin_api_token=<отдельный случайный токен минимум 32 символа>
wg_server_public_key=<проверенный публичный ключ сервера>
wg_ssh_host=<проверенный адрес VM 101>
wg_ssh_port=22
wg_ssh_user=avantime-wg
wg_ssh_key_file=<абсолютный путь к ограниченному SSH-ключу>
wg_ssh_known_hosts=<абсолютный путь к заранее проверенному known_hosts>
wg_endpoint=<проверенный VPN endpoint>
wg_allowed_ips=<разрешённые сети профиля>
rdp_host=<проверенный RDP host>
```

Эффективные настройки берутся только из указанного файла, не из окружения оболочки
или обычного .env. Остальные значения — defaults выбранного исходного config.py;
при необходимости указать их явно. Обычные значения защиты reserved_ips не ослаблять.
`--public-key-file` содержит **только публичный** WireGuard-ключ комплекта.
Приватный VPN-ключ остаётся у оператора/тестового клиента, backend он не нужен.

Из admin-backend, в окружении с установленными requirements.txt:

```bash
python -m integration.fault_backend \
  --env-file /absolute/private/test-d.env \
  --public-key-file /absolute/private/test-d.pub \
  --control-dir /absolute/private/run-d \
  --fault before-add --timeout 90
```

Все пути — шаблоны, не существующие серверные пути. Родитель control-dir должен
существовать, сама control-dir — **не существовать**. Инструмент создаёт её с 0700,
manifest и events.jsonl — с 0600. Повторное использование каталога запрещено, чтобы
старый файл `release` не открыл новую задержку. Использовать один процесс инструмента
для одного комплекта. После `backend_starting` дополнительно дождаться успешного
startup и GET `/api/health` (200), прежде чем создавать пользователя/приглашение.

Все add/remove ограничены выбранными key/IP и первым валидным owner. Для другого
ключа/IP/owner вызова SSH не будет. Status использует настоящий штатный транспорт.
Owner сохраняется только в процессе и локальном журнале; авторитетная проверка
владения остаётся в helper. При перезапуске для очистки — тот же key/IP/тестовая БД,
новая control-dir, режим `none`; helper снова сверит owner с managed.json.

| --fault | Поведение |
|---|---|
| none | Настоящие add/remove; ограничение одним комплектом сохраняется |
| before-add | D: после появления pending удерживает add до SSH; после release возвращает ошибку, add не отправляется |
| drop-add-response | E: настоящий add и проверка контракта, затем ошибка до pending→active |
| delay-add-response | J: настоящий add и проверка контракта, удерживает успешный ответ; после release enroll продолжает обычный CAS/компенсацию |

В режимах со сбоем разрешена только одна попытка add за процесс. Повторный enroll
не обходит инъекцию и не активирует pending; remove остаётся доступен. Инструмент
не подделывает `created` или `absence_confirmed`. Событие `add_returned` означает
полученный и проверенный ответ helper, но не заменяет независимые реальные снимки.
Событие `remove_confirmed` записывается только после штатной валидации remove.

## Выполнение сценариев и фиксация результата

API-запросы направлять только на локальный порт изолированного backend. Административные
запросы требуют его отдельный Bearer; enroll — test token/key/device. Не выводить
секреты в shell history, HTTP debug, отчёт или Git. Timeout клиента для D/J должен
превышать выбранные 90 секунд. Инструмент не выполняет сценарии автоматически.

### Комплект 1, режим none

- A: создать тест-пользователя и приглашение, enroll → 200. Mongo pending→active;
  peer в runtime/конфиге с IP1/32, managed active, owner/IP соответствуют.
- B: повтор того же token/key/device в ENROLL_RECOVERY_TTL (86400 секунд по умолчанию)
  → 200, идентичный сохранённый профиль, один peer и один выделенный IP.
- C: отдельно изменённый key, отдельно device_name → 409.
- I: через тот же ограниченный SSH helper отправить add и remove с тестовыми
  key/IP1, но другим валидным UUID owner. Оба должны дать `ok:false` с
  `Peer belongs to another operation`; существующий тест-peer и боевые peers целы.
  Через API подмена owner невозможна; harness намеренно блокирует такой вызов.
- F: API revoke → 200 только с подтверждённым удалением. Нет peer в runtime/конфиге;
  managed и тест-Mongo revoked, IP занят.
- G: повтор revoke → 200, отсутствие подтверждается снова, tombstone сохраняется.
- H1: исходный завершённый enroll после revoke → 410 без профиля.
- H2: ограниченный helper, add с прежними key/IP1/owner → `ok:false`,
  `Revoked peer cannot be reactivated`; peer не появляется.

Для закрытия гейта фиксировать H1 и H2 отдельно, выполнить оба.

### Комплект 2, D, режим before-add

1. Создать пользователя/приглашение; отправить enroll, оставив запрос в полёте.
2. Дождаться события `before_add` в events.jsonl. Записать созданный owner.
   Проверить Mongo pending и отсутствие тест-peer в config/runtime; до отмены
   записи этого ключа в managed.json ещё нет. Не изменять состояние Mongo вручную.
3. Параллельным HTTP-запросом вызвать revoke → 200; проверить отсутствие peer,
   revoked в тест-Mongo и owned tombstone в managed.json.
4. Пока барьер не истёк, в отдельном локальном терминале:

```bash
touch /absolute/private/run-d/release
```

5. Дождаться завершения исходного enroll → 502, событие `add_not_sent`.
   Повторно проверить revoked/отсутствие peer. Повтор этого enroll → отказ 409.

Если барьер истёк раньше нужной контрольной точки, результат сценария не засчитывать;
add не отправляется, но pending следует довести обычным revoke до подтверждённого
revoked. Не освобождать IP и не удалять tombstone ради повторного теста.

### Комплект 3, E, режим drop-add-response

1. Новый комплект и тестовая БД, создать пользователя/приглашение, enroll.
2. Получить 502; в events — `add_returned`, затем `add_response_dropped`.
   До revoke снять одну согласованную контрольную точку: тест-Mongo pending,
   managed active, настоящий peer в config/runtime с IP3/32. Это намеренное
   временное расхождение состояний и предмет теста.
3. API revoke → 200, подтвердить отсутствие и оба revoked. Повтор revoke → 200;
   повтор отменённого pending enroll → 409. Резервы и tombstone сохраняются.

Если настоящий SSH/add сам завершился ошибкой, событие `add_response_dropped`
не появляется: сценарий E не воспроизведён. Проверить неизвестный исход и выполнить
подтверждённый revoke; не выдавать транспортную ошибку за успешную инъекцию.

### Комплект 4, J, режим delay-add-response (дополнительно)

Дождаться `add_response_held`: Mongo pending, peer применён. Вызвать revoke и
подтвердить revoked/отсутствие. Создать release в control-dir этого запуска.
Исходный enroll должен завершиться 410, пройти компенсирующий remove (в журнале
два `remove_confirmed`: отзыв и компенсация); конечное — revoked/нет peer.
404 до появления устройства не считается проверкой отзыва. Любой active после
принятого отзыва — провал. Отдельный interleaving поздней доставки add покрыт
mock-регрессиями; этот реальный режим специально проверяет поздний успешный ответ.
Сценарий K с намеренной внешней правкой общего конфига — только на отдельном стенде.

## Снимки, завершение и отчёт

До теста, в указанных контрольных точках и после каждого сценария сравнить
нормализованные public keys, AllowedIPs и статические параметры интерфейса.
Handshake, счётчики и roaming endpoint штатно меняются. Боевые peers сравниваются
отдельно от тестовых. Не сохранять сырые конфиги/`wg dump` в отчёт: там могут быть
PrivateKey/PSK. Полные резервные копии, если нужны оператору, остаются защищёнными
и не используются для автоматического восстановления общего состояния.

По окончании каждого комплекта: peer отсутствует в runtime и конфиге;
managed.json и тестовый device содержат revoked; production marker и тестовый
vpn_ip сохранены. Не удалять tombstones, тестовую БД или production-резервы.
Остановить только изолированный backend после подтверждённой очистки. Если remove
не подтверждён — тест не завершён, состояние revoking сохраняется, требуется повтор
и разбор; завершение процесса не удаляет реальный peer.

Отчёт: SHA и manifest, hash установленного helper, подтверждение изоляции БД и
production-резервов, таблица A–I/H1/H2 (ожидание/факт/HTTP-код/снимки), отдельно J/K,
нормализованное сравнение боевых peers и конечное состояние каждого комплекта.
Токены, приватные ключи и секреты исключить. Любой недоступный сценарий отметить
непроверенным с причиной. PR остаётся draft; снятие draft/merge возможно только
после отдельного подтверждения реального прогона и конечных инвариантов.
